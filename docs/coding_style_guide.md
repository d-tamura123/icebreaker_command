# コーディング規約(コメント・命名編)

このドキュメントは、`icebreaker_command`プロジェクトにおける「コメントの書き方」「変数・関数の命名方針」をまとめたものです。
人間のレビュー用であると同時に、**AIにコードを書かせる/レビューさせる際にそのまま指示として読み込ませることを想定**しています。
以下のルールは、自分が過去に手掛けた別プロジェクトのコードを分析し、そこで自然と行っていたコメントの書き方を言語化・体系化した上で、本プロジェクトで独自に強化したものです。

---

## 0. 基本方針(最重要)

- コードは「今の自分」ではなく、**数ヶ月後に読み返す自分、あるいは初めてこのファイルを読む他人**が対象読者だと想定して書く。
- コメントは「コードが何をしているか(What)」だけでなく、**「なぜそうしているか(Why)」を優先して書く**。Whatはコードを読めば分かるが、Whyは書かないと失われる。
- 数式・数学的ロジックが絡む処理は、**式を省略せずに書き下し、処理を追わなくても意図が伝わる**ことを目指す。
- 変数名・関数名は、**「何を求めたいか」「何を表しているか」を名前だけで推測できる**ことを目指す。処理を1行ずつ追わなくても、宣言と代入を見ただけで意味が分かるようにする。
- 「読めば分かる」を理由にコメントを省略しない。冗長に見えても、意図の言語化を優先する。

## 1. 基本フォーマット(インデント・桁揃え)

- インデントは**半角スペース4個を1段**とし、タブ文字は使用しない(エディタの「Tabキー入力時にスペースへ変換」設定を有効にすること)。タブ文字が混在すると、環境によってタブ幅の解釈が異なり、桁が揃って見えたり見えなかったりする原因になる。
- 定数・メンバ変数・引数などの縦の桁揃え(7節・8節参照)は、**最終的に人間がエディタで開いたときに、実際に縦の列として揃って見えること**をゴールとする。
- 桁揃えの手順:
  1. 揃えたいブロック内で、最も長い「型名+変数名」等の文字数を数える
  2. 他の行に、実際の文字数ベースでスペースを補って`=`や`//`の位置を揃える(目視の感覚だけで挿入すると簡単にズレるため、必ず文字数を数えること)
  3. 可能であれば、ファイルを実際に開いて縦の列が揃っているかを目視で最終確認する
- 桁揃えの対象は、**半角文字であるコード部分(`//`が始まる位置まで)に限定**する。コメント本文の日本語(全角文字)は、フォントやエディタによって表示幅の扱いが変わるため、コメント文中でさらに厳密な桁揃えを行うことは求めない。

## 2. ファイルヘッダー

すべての`.h`/`.cpp`ファイルの先頭、`#pragma once`や`#include`より前に、ファイル名だけの1行コメントを入れる。

```cpp
// gmProjectileBase.h
#pragma once
#include "gmObjectBase.h"
```

```cpp
// gmProjectileBase.cpp
#include "gmProjectileBase.h"
```

クラスの役割が一言で説明できる場合は、2行目に短い説明を続けてもよい(必須ではない)。

```cpp
// gmGhost.cpp
// ゴースト敵キャラクタークラス
```

## 3. セクション区切り(ファイル/クラス粒度)

ファイル内で「これはクラス／構造体／機能のまとまりの説明である」と示したい箇所は、ダッシュ罫線で囲んだブロックコメントを使う。罫線の長さは60文字程度(`-`を60個前後)で揃える。

```cpp
// ------------------------------------------------------------
// 「クリックした地点まで放物線を描いて飛ぶ」弾道兵器の共通基底クラス。
//
// ここに集約するのはあくまで軌道計算(飛行時間・山なりの高さ・重力/初速の
// 逆算・毎フレームの位置更新)とタイミング管理だけで、見た目の構築・更新・描画、
// および着弾時の効果(溶かす/割る等)は派生クラス側の責務とする。
// ------------------------------------------------------------
class gmProjectileBase : public gmObjectBase {
```

用途:
- クラス・構造体の直前(役割の説明)
- ファイル内の関数群のまとまりの直前(例: 「ユーティリティ関数」「軌道計算」等)
- 個々の関数の直前(その関数が何をするか、1〜数文で要約。詳細は4節・6節を参照)

## 4. 関数内の小段落区切り(手順)

1つの関数の中で処理が複数の意味的なまとまりに分かれる場合、罫線より軽量な区切りとして`// ---- ラベル ----`(ダッシュ4個程度)を使う。

```cpp
// ---- 手順1: 発射位置から着弾位置までの「水平距離」を求める ----
const float horizontalOffsetX = targetPos.x - startPos.x;
...

// ---- 手順2: 水平距離から「飛行時間(滞空時間)」を求める ----
...
```

**処理が3ステップ以上に分かれる長い関数では、必ず「手順1」「手順2」…と番号を振り、対応する処理ブロックの直前に同じ番号のコメントを置く。** 関数のトップ(罫線ブロック内)に手順の一覧を先出しし、本文側にも同じ番号を繰り返すと、全体像と詳細の対応が取りやすい。

```cpp
// ------------------------------------------------------------
// コンストラクタ。(中略)
// 処理は大きく4段階に分かれる。
//   手順1: 発射位置から着弾位置までの「水平距離」を求める
//   手順2: 水平距離から「飛行時間(滞空時間)」を求める
//   手順3: 水平距離から「山の高さ(頂点の高さ)」を求める
//   手順4: 飛行時間と山の高さから、初速度と見かけの重力を逆算する
// ------------------------------------------------------------
gmProjectileBase::gmProjectileBase(...)
{
    // ------------------------------------------------------------
    // 手順1: 発射位置から着弾位置までの「水平距離」を求める。
    // (詳細な説明...)
    // ------------------------------------------------------------
    ...
}
```

## 5. 関数・処理ブロックの説明順序

**「まず何がしたいか」を噛み砕いた1文で要約し、その後に詳細なロジック・数式の解説を続ける。** 結論を先に、詳細を後に書く(結論から書く「逆ピラミッド」形式)。

```cpp
// ------------------------------------------------------------
// 毎フレームの更新。経過時間から弾の現在位置・進行方向を計算し、
// 見た目の更新(派生クラスのupdateVisual)へ橋渡しする。
// 着弾したら位置を目標地点に確定させて消滅させる。
// ------------------------------------------------------------
void gmProjectileBase::update(float deltaTime)
{
    ...
}
```

## 6. コメントの粒度

- ほぼ全ての非自明な行に、「何を求めている行か」を一言添える。特に「その行の結果が何を意味するか」を書く(処理内容の言い換えではなく、意味の説明)。
- 「なぜその簡略化・近似・実装方針が成り立つか」を必ず書く。例: 「正規化済みなので長さ1として扱える」「表裏両方描画するため実質2倍の方向から見える」等。
- 一時的なメモ書き(「静かに無視する」「今後ここに追加」等)は許容するが、コードの意図を損なわない範囲にとどめる。

良い例:
```cpp
const float halfAngle = (angleDeg * DX_PI / 180.0f) / 2.0f; // 扇形の半分の角度(ラジアン)
```

避けたい例(コードをそのまま日本語に置き換えただけ):
```cpp
const float halfAngle = (angleDeg * DX_PI / 180.0f) / 2.0f; // angleDegを2で割る
```

## 7. 引数コメント

引数が2つ以上ある関数・コンストラクタは、**1引数につき1行の`// arg番号...`コメントを、引数リストの直前にまとめて書く**。

```cpp
// arg1... 識別ID
// arg2... 発射位置(ワールド座標)
// arg3... 着弾目標位置(ワールド座標)
// arg4... 水平方向の速さ(world単位/秒)。近距離〜基準距離まではこれで飛行時間が比例して伸びる
// arg5... 山の高さ ÷ 水平距離 の比率。大きいほど山なりが大きくなる
// arg6... 当たり判定(球)の半径
gmProjectileBase(
    const std::string& id,
    const tnl::Vector3& startPos,
    const tnl::Vector3& targetPos,
    float horizontalSpeed,
    float arcHeightRatio,
    float colliderRadius
);
```

各引数の説明には、可能な限り以下を含める:
- 単位(world単位、秒、度数法 等)
- 前提条件(正規化済みを想定 等)
- 具体例(「例: 165度 → 前方165°の扇形範囲」等)

引数を関数定義の各行末にコメントする場合も、同様に1引数1行とし、`//`の桁を揃える(8節参照)。

## 8. 定数・メンバ変数のコメントと桁揃え

- 定数・メンバ変数は、**同じブロック内で`//`の桁を縦に揃える**。
- 単位・意味を必ず末尾コメントに書く。

```cpp
static constexpr float MIN_FLIGHT_TIME           = 0.3f;  // 極端に近い的でも最低これだけの飛行時間を確保する(秒)
static constexpr float ARC_TIME_LINEAR_PHASE_SEC = 1.2f;  // この秒数ぶんの距離までは「距離÷水平速度」の比例。それより遠いとゆるやかな伸びに切り替わる
```

**注意(実務上の落とし穴)**: 桁揃えは目視でスペースを数えて挿入すると簡単にズレる。揃える際は、対象ブロック内で最も長い識別子(またはコード部分)の文字数を基準に、他の行へ機械的に(実際の文字数を数えて)スペースを補うこと。AIが生成する場合も同様に、目視の見た目ではなく文字数ベースで揃えること。

## 9. 変数・関数の命名

- **ワーク変数は「何を求めたいか」を表す名前で宣言し、その変数へ答えを代入する形で処理を書く。** 処理を1行ずつ追わなくても、宣言を見ただけで「これは何を表す値か」が分かることを目指す。
- `dx`, `dy`, `dz`, `dt`のような数学の省略記法は、**業界的には広く使われており、"手抜き"ではない**。ただし、以下のいずれかに該当する場合は、意味のある名前を優先する。
  - コードが長期間読み返される想定である(本プロジェクトはこちらの方針を採用)
  - 変数の生存期間が長い、または離れた場所で再利用される
  - コメントを読まずに変数名だけで意味が伝わってほしい

  例:
  ```cpp
  // 避ける(このプロジェクトの方針では)
  const float dx = targetPos.x - startPos.x;
  const float dz = targetPos.z - startPos.z;

  // 推奨
  const float horizontalOffsetX = targetPos.x - startPos.x;
  const float horizontalOffsetZ = targetPos.z - startPos.z;
  ```

- ループ変数等の一時変数も、`p`, `i`, `t`のような単文字より、`projectile`, `planeIndex`, `blendFactor`のように意味を示す名前を優先する(ループのインデックスとして真に一時的・自明な`i`はこの限りではないが、意味を持たせられるなら持たせる)。
- 既存クラスとの整合性(継承関係、呼び出し元との対応)を壊さない範囲で、命名変更は**変数・関数名のみ**にとどめ、ロジック自体は変更しない。

## 10. 数学的ロジックの説明

- 数式は省略せず書き下す。「ラジアンに変換する」ではなく、実際の式を書く。

  ```cpp
  // ラジアン変換公式: θ[rad] = θ[deg] × π / 180
  ```

- 「なぜその式・簡略化が成り立つか」を一緒に書く。

  ```cpp
  // 内積公式: a・b = |a||b|cosθ
  // 正規化済みなので |a|=|b|=1 → a・b = cosθ
  ```

- 説明の難易度は「特定の学年で習う」といった前提を持ち出さず、素直に「数学の公式」「物理の公式」のように書く(読み手の教育背景を決めつけない)。
- 教科書に載っている有名な定理は、名称を出して簡潔に済ませてよい(例: 「三平方の定理(ピタゴラスの定理)」「等加速度運動の位置の式」)。ただし、**その式自体は省略せず書く**。名称だけで式を省略しない。
- 独自に設計した式(ゲーム側の都合で物理法則から意図的に外れている部分等)は、「なぜ物理法則通りにしなかったか」の意図も書く。

  ```cpp
  // ※ 物理法則(重力)通りに計算すると、遠距離ほど山なりが過剰に高く・
  //    長い滞空時間になってしまい見た目が不自然だったため、あえてこのような
  //    独自のカーブ(ゲームとして気持ちよく見える形)を設計している。
  ```

## 12. 設計判断は、実装前に選択肢を提示し合意を得る

AI(特にClaudeのような自律性の高いモデル)は、指示があいまいな場面でも「もっともらしい」実装方針を自分で判断して進めてしまう傾向がある。しかしゲーム制作においては、**設計・演出上の「どれを選ぶか」自体がユーザー体験(操作感・見た目・演出のテンポ等)に直結する**ため、AIが妥当と判断した選択肢が、必ずしも作り手の意図に合うとは限らない。以下に該当する場合は、実装に着手する前に必ず選択肢を提示し、それぞれの利点・欠点・トレードオフを添えた上で、合意を得てから進めること。

**選択肢の提示・合意が必要なケース:**
- 同じ要件を満たす実装方法が複数考えられ、どれを選ぶかがゲームの触り心地・見た目・演出意図に影響する場合
  (例: エフェクトの表現方法をサイン波にするか、バネのような遅延追従にするか)
- クラス設計・継承構造など、後々の拡張性に影響する構造的な判断
  (例: 機能追加のたびに基底クラスを増やすか、既存クラスにフラグ分岐で対応するか)
- 見た目・演出・パラメータ調整など、感覚的・主観的な判断が伴う場合
  (例: 色調、揺れの強さ、使用するエフェクト素材の選定)
- 一度実装すると後戻りのコストが大きい判断
  (既存クラスの分割・大規模なリファクタリング等)

**選択肢の提示・合意が不要なケース(判断して進めてよい):**
- 明確に直し方が一つしかないバグ修正
- 挙動を変えないリファクタリング(コメント・命名の変更のみ等)
- 既に合意済みの設計方針の範囲内で、その続きを実装する場合
- 依頼者が明示的に「任せる」「好きにしてよい」と言った場合

判断に迷う場合は、「これは選択肢を提示すべき場面か?」を自問し、**迷ったら提示する側に倒す**こと。

## 13. その他の方針

- 過去の実装や別案をコメントアウトしたまま残す慣習が別プロジェクトには見られたが、**本プロジェクトでは基本的に踏襲しない**(コードが読みにくくなるため)。設計判断の経緯を残したい場合は、コメントで理由を書く形にとどめ、デッドコードとしては残さない。
- 設計判断の合意プロセスについては12節を参照。

## AIへの指示として使う場合のチェックリスト

新規コード生成・既存コードのコメント修正を依頼する際は、以下を満たしているか確認すること。

- [ ] ファイル冒頭にファイル名コメントがあるか
- [ ] インデントがスペース4個(タブ不使用)で統一されているか
- [ ] クラス・大きな関数群の前に罫線区切り+要約コメントがあるか
- [ ] 3ステップ以上の処理に「手順N」のラベルが振られているか
- [ ] 各関数の冒頭が「一文要約→詳細」の順になっているか
- [ ] 引数が2つ以上ある関数に、1引数1行の`arg番号...`コメントがあるか
- [ ] 定数・メンバ変数ブロック内で`//`の桁が(実際の文字数ベースで)揃っているか
- [ ] `dx`/`dy`等の省略変数名を、意味の分かる名前に置き換えているか(このプロジェクトの方針)
- [ ] 数式が省略されず書かれているか、「なぜその式が成り立つか」まで書かれているか
- [ ] 読み手の教育背景を決めつける表現(「〇〇なら分かる」等)がないか
- [ ] ロジック自体を変更していないか(コメント・命名変更のみを依頼された場合)
- [ ] 実装方針に複数の選択肢がありうる設計判断を、確認なしに独断で進めていないか(12節参照)
